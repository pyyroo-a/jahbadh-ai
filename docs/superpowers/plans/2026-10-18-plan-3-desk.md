# Jahbadh Plan 3: The Desk Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The live match desk people actually watch. A FastAPI backend streams a match and the agents' grounded feed over Server-Sent Events in two modes: **replay** (the default: a real, precomputed desk run on the demo match, free and instant) and **live** (a fresh match where the agents really run, with guardrails on cost). A React desk UI shows the event stream, a tactical pitch, and the agent feed, where every claim opens up its evidence.

**Architecture:** Python builds one ordered **timeline** per match: every event (with template lines in EN, AR and ES), a match-state snapshot every minute, and the desk's moments. The SSE endpoint plays a timeline at a chosen speed. Replay reads `data/showcase/match-042/desk.json`, and live mode runs Plan 2's `run_moment` as the clock reaches each key moment. The browser keeps a single reducer over the stream messages. Everything the UI draws comes from those messages: metrics, events and renders. The UI never computes a football number itself.

**Tech Stack:** Python 3.13, FastAPI 0.143.3 (built-in SSE via `fastapi.sse`), uvicorn 0.54.0, pydantic v2, pytest with Starlette's `TestClient` on `httpx2`. Web: Node 22.14, Vite 8.3, React 19, TypeScript 6.0 (as the `react-ts` template ships it), Vitest 5.0, hand-written SVG and CSS (no UI kit, no chart library).

**Spec:** `docs/superpowers/specs/2026-10-17-jahbadh-design.md` (sections "Pacing", "API and UI", "Keeping the demo alive and cheap"). The layout follows the mockup at `.superpowers/brainstorm/617-1792227804/content/desk-layout.html`, which is gitignored.

- Python 3.13. New runtime deps only: `fastapi>=0.143,<1` and `uvicorn>=0.54,<1`. New dev dep: `httpx2>=2.13`. There's no `sse-starlette`, because FastAPI's own `fastapi.sse` does the job.
- Web: Node `>=22.12`, plus the template's versions (vite 8, react 19, typescript ~6.0) and `vitest@^5`. No other npm runtime deps.
- **Unit tests never call Azure.** Python uses `ScriptedChatClient` and `FakeTranslator` from `tests/agents/fakes.py`, and the API tests inject a scripted desk factory and a no-op sleep.
- **Every SSE test reads a stream that ends** (it ends at `end`), and every live test runs inside `with TestClient(app) as client:`.
- **Test file basenames must be unique across `tests/`.** This is pytest's prepend import mode with no `__init__.py`. New API tests are named `tests/api/test_api_*.py`. - **No future leakage in live mode:** the server never sends an event, a state or a moment before the clock reaches its `t`. Replay's `match` message carries only the `moment_times` (no labels or kinds), for "skip to next moment".
- **Replay is honest:** the UI labels it "Replay · precomputed by the real desk". The showcase `desk.json` is real pipeline output and never hand-edited.
- **Cost guardrails:**
  - Live mode is off unless `JAHBADH_LIVE_MODE=on`.
  - 3 live actions a day across all users (`JAHBADH_LIVE_PER_DAY`). A fresh match and a spotlight each count as one, and the counter is persisted in `JAHBADH_STATE_DIR` and fails closed.
  - Only one live run at a time; a second start joins it for free.
  - Key moments only, at concurrency 3.
  - At most 2 extra persona and language combos per live run.
  - A live run with no viewers for 60 s is cancelled.
- **Simulator changes never change a match.** New simulated fields come from deterministic values or their own seed-derived random stream, never from the match RNG. A fingerprint test (Task 1a) pins seeds 42, 1 and 7.
- **Synthetic is labelled synthetic:** shot speed, the pass success odds and the tracking-based speeds are shown and documented as coming from the simulator.
- **Data-true:** template lines state exactly what the event says, and the UI shows the agents' text and the computed numbers. Nothing gets reworded or invented in the browser.
- **Copy:** friendly, with no em dashes. That covers UI strings, template lines in all three languages, the README and commit text.
- **Commits:** the user commits every change through GitHub Desktop. Each task ends with commit instructions (files to tick, Summary, Description), and the next task waits for "committed". Never run `git commit` or `git push`.

### Stream protocol (both modes)

Each SSE message is `event: <kind>`, `id: <index>` and `data: <JSON>`. Index 0 is always `match`, and timeline items are numbered from 1.

| kind | data (Python model, `jahbadh.api.stream`) | when |
|---|---|---|
| `match` | `MatchInfo{match_id, mode: "replay"\|"live", home: Team, away: Team, speed, precomputed: bool, model, created, moment_times: list[float]}` | first, unless resuming |
| `event` | `EventLine{id, t, minute, type, team_id, player_id, related_player_id, x, y, end_x, end_y, outcome, xg, lines: {en, ar, es}}` | at `t` |
| `state` | `MatchState{t, minute, score, xg, momentum, field_tilt, ppda, shape, formations}` | t = 0, 60, ..., 5400 |
| `thinking` | `Moment` | the desk starts a moment |
| `feed` | `FeedItem` (Plan 2) | the moment published |
| `failure` | `MomentFailure` (Plan 2) | the moment failed |
| `renders` | `RendersUpdate{moment_id, renders, rejections}` | live: an extra combo is ready |
| `end` | `StreamEnd{reason: "full_time"\|"cancelled"}` | last |

Within one `t`, the order is event, thinking, state, then feed or failure. In replay, `thinking` comes at `moment.t` and `feed` at `moment.t + 20` match seconds (`REPLAY_DESK_LAG_S`). That way the "desk is thinking" state is visible, and the badge still says precomputed.

### Task 1a: Simulator fields: pass success odds and a synthetic shot speed (no match changes)

**Interfaces:**
- PASS events gain `detail["p_success"] = round(p_ok, 4)`. That's the success probability `pass_ball` already computes (between 0.3 and 0.97). It costs no random draw.
- SHOT events gain `detail["speed_kmh"]`, which is **synthetic**. `shot_speed.py` has:
  - `SHOT_SPEED_STREAM = 0x5407`
  - `shot_speed_kmh(rng: np.random.Generator, distance_m: float) -> float`, which gives `clip(normal(55 + 1.2 * distance_m, 12), 35, 125)` rounded to 1 decimal. Close finishes come out slower and placed, and long shots approach max-effort kicks. The docstring says it's synthetic, and cites the small lab study of national-team players with max-effort kicks of about 102 to 115 km/h (https://wnus.usz.edu.pl/cejssm/file/article/download/20440.pdf). No large match dataset was found, so it says that too.
  - `add_shot_speeds(match: Match, seed: int) -> None` draws from `np.random.default_rng([seed, SHOT_SPEED_STREAM])`, its own stream, in event order. The distance is from the shot location to the centre of the goal it attacks.
- `simulate_match` calls `add_shot_speeds` **after** `_Engine.run()` returns, so the match RNG never sees it.
- `tests/simulator/test_fingerprint.py`: `fingerprint(match: Match) -> str` is a sha256 over every event's `model_dump(mode="json")` with `p_success` and `speed_kmh` removed from `detail`, plus the tracking frame's `pd.util.hash_pandas_object(..., index=False)` values. `fingerprints.json` holds seeds 42 (demo storyline), 1 and 7 (none).

### Task 1b: Player speed, distance and alerts

**Files:**
- Create: `src/jahbadh/analytics/physical.py`, `tests/analytics/test_physical.py`
- Modify: `src/jahbadh/analytics/__init__.py` (exports)

**Interfaces:**
- `MAX_HUMAN_KMH = 40.0`: a one-second step faster than this is the simulator snapping the ball carrier onto the ball, not running. These steps are excluded and counted (measured 18 Oct: 30 of 118,800 steps on the demo match).
- `SPRINT_RECORD_MIN_KMH = 30.0` and `DISTANCE_MILESTONES_KM = (5.0, 10.0)`
- **Speed rule (user decision, see the update notes):** speed is the raw 1 Hz step length, so a one-second step of `d` metres is `d * 3.6` km/h. Distance is the sum of the kept steps.
- `player_physical(match: Match, player_id: str, start: float = 0, end: float = 5400) -> Metric`:
  - `name="physical"`, `unit="km"`, value = distance in km (`None` if they weren't on the pitch)
  - `data = {"distance_km", "top_speed_kmh", "top_speed_t", "minutes", "excluded_steps"}`
  - `evidence_frames=frame_range(start, end)`, and it checks the window.
- `physical_alerts(match: Match, end: float = 5400) -> list[Metric]`, sorted by `t`:
  - `name="sprint_record"` each time a player sets a new **match-wide** top speed of at least 30 km/h (value = km/h, window = `(t - 1, t)`).
  - `name="distance_milestone"` the first time each player passes 5 km and 10 km (value = the milestone in km, window = `(0, t)`).
  - Each alert's subject is the player, and its id is `metric_id(name, player, start, end)`.

### Personalisation: what needs the model and what doesn't

The rule is to reuse what the Referee already approved (filter, order, highlight), and to pay for new text only where there's no other way. The paid run in Task 3 already includes everything listed here, so nothing gets paid for twice.

| Mode | What the viewer gets | New LLM text? |
|---|---|---|
| Favourite club | Claims about their club first and badged, the rest kept but dimmed, the club's own full-time recap first, and its stats in the tiles | **Yes, once:** two `team_recap` moments (one per club) in the showcase run (Task 2a), about +15 cents, in all 9 combos. The feed itself is just tags and ordering in the browser. |
| Favourite player / follow | One player through the whole match: their events lit up, live distance, top speed, xGI, pass difficulty and touches, their heatmap so far, and every approved claim involving them | No. These are computed numbers (Task 2b) plus filtered claims. The narrative comes from the 3 precomputed spotlights in replay, and from a paid on-demand spotlight in live mode (already in Task 8). |
| Single metric | One metric (xG, PPDA, field tilt, momentum, pass difficulty or game rhythm) as a big tile with its minute-by-minute line, plus every claim that cites it | No. It reads the match states (Task 5a) and filters claims by metric name. |

Tagging a claim with teams and players needs nothing new from the server. The browser already has the cited events (with team and player), the cited metrics (with subject) and both squads, so `claimTags` (Task 10a) works it out on the client.

### Task 5: The stream protocol and the match timeline

**Files:**
- Create: `src/jahbadh/api/stream.py`, `src/jahbadh/api/timeline.py`
- Test: `tests/api/test_api_timeline.py`

**Interfaces:**
- `stream.py`: the models from the Stream protocol table, field for field. Also:
  - `StreamKind = Literal["match", "event", "state", "thinking", "feed", "failure", "renders", "end"]`
  - `@dataclass(frozen=True) class StreamItem: t: float; kind: StreamKind; data: BaseModel`
  - `to_sse(index: int, item: StreamItem) -> ServerSentEvent` (event = kind, id = `str(index)`, data = the model)
  - `MatchState.momentum` is the home share of threat over the last 10 minutes. `field_tilt` is the home team's share over the same window. `ppda` is keyed by the defending team. `shape` holds `average_positions` metrics keyed by team, over the last 10 minutes and in the attacking frame. `formations` comes from `formation_at`.
- `timeline.py`:
  - `REPLAY_DESK_LAG_S = 20.0`
  - `match_state(match: Match, t: float) -> MatchState`: the window is `[max(0, t - 600), t)`. At `t == 0` everything is empty: score 0-0, xG 0.0, momentum, tilt and PPDA all `None`, and `shape` is `{}`. Score comes from `score_at`, and xG from `xg_total(match, team, 0, t)`.
  - `event_line(match: Match, e: Event) -> EventLine`
  - `match_timeline(match: Match) -> list[StreamItem]`: every event, plus a state at each of t = 0, 60, ..., 5400 (91 states). It's sorted by `(t, order)` with event 0, thinking 1, state 2, feed and failure 3. It has no `match` or `end` item; `app.py` and `live.py` add those.
  - `replay_timeline(show: Showcase) -> list[StreamItem]`: `match_timeline`, plus `thinking` at `moment.t` and `feed` at `moment.t + REPLAY_DESK_LAG_S` for every desk item, plus `end` (`full_time`) after the last item. Failed moments simply don't appear.

    - `clock: float`, `done: bool`
    - `start() -> None` creates the run task. It plays `match_timeline(match)` through the same pacing rule as `paced`. When the clock passes a key moment's `t`, it appends `thinking` and starts `run_moment(desk, moment)` under a `Semaphore(LIVE_CONCURRENCY)`, then appends `feed` or `failure` stamped with the clock at completion. Once the timeline and every moment are done, it appends `end` (`full_time`).
    - `async subscribe(start: int = 0) -> AsyncIterator[tuple[int, StreamItem]]` yields the history from `start`, then waits for new items (an `asyncio.Event` set on every append) and stops after `end`. It counts subscribers while it runs.
    - `skip() -> float | None` moves the clock to `next moment t - SKIP_LEAD_S` and wakes the pacing sleep (the sleep races an `asyncio.Event`). Events in between still go out, as a burst. It returns `None` when no moment is left.
    - `async spotlight(player_id: str) -> Moment` builds `spotlight_moment(match, player_id, "requested by a viewer", t=clock)` with the id `f"spotlight-{player_id}-{int(clock)}"` and runs it like any moment. It raises `KeyError` for an unknown player.
    - `add_combo(persona: Persona, language: Language) -> bool` is False once `LIVE_MAX_COMBOS` extra combos exist (pundit/en doesn't count). Otherwise it renders the combo for every published item with `render_combo` in the background, appends one `renders` item per moment, and makes every later `feed` get it too.
    - `async cancel() -> None` cancels the pending moments and appends `end` (`cancelled`).
    - **Idle rule:** before each paced item, and every second while waiting on the last moments, if nobody has been subscribed for `idle_s` (measured with `now()`), the run calls `cancel()`.

  - `zoneRect(zone: string, isHome: boolean): { x: number; y: number; w: number; h: number }`, in SVG coordinates. The `zone` is `"<third>-<lane>"`, with thirds `defensive [0,35)`, `middle [35,70)` and `final [70,105]`, and lanes in the attacking frame `left [2W/3, W]`, `centre [W/3, 2W/3)` and `right [0, W/3)`.
- `layers.ts`: `type Layer = { kind: "heat"; cells: { x; y; w; h; v }[] } | { kind: "dots"; dots: { x; y; label; team }[] } | { kind: "network"; nodes: ...; edges: ... } | { kind: "shots"; shots: { x; y; xg; goal }[] } | { kind: "zone"; rect; label } | { kind: "none" }`.
  - `metricLayer(m: Metric, info: MatchInfo): Layer`. It handles heatmap (only cells with v > 0), average_positions, pass_network (only edges whose two nodes exist and have a `pos`; Task 1 lets `pos` be `None` for hand-built data), shot_map and zone_overloads (`data.zone`, labelled with `data.typical`, e.g. "3v1"). The subject resolves to a team by id, or to a player through `info.home/away.players`. Anything else returns `{kind: "none"}`.
  - `eventLayer(events: EventLine[]): { arrows; points }`: passes and carries with an end point become arrows, the rest become points. These use raw coordinates through `toSvg`.
- `format.ts`: `formatMetric(m: Metric, info: MatchInfo): { value: string; label: string; sub: string }`.
  - Shares (`share`, `home_share`, `share_of_seconds`) become `${Math.round(v * 100)}%`. `xG` and `xGI` get 2 decimals, `passes/def_action` 1 decimal, `m` 1 decimal plus " m", and counts are integers. A `null` value reads `"no data"`.
  - Labels: field_tilt "Field tilt", ppda "PPDA", momentum "Momentum (home share)", xg_total "xG", player_impact "xG involvement", heatmap "Heatmap", average_positions "Average positions", zone_overloads "Overload", pass_network "Pass links", shot_map "Shots", match_stats "Match stats", attacking_sides "Attacking side", midfield_control "Midfield control". Any other name is shown as is, with underscores turned into spaces.
  - `sub` is the subject's name and the window as "61' to 75'".
- `TacticalView`:
  - With no selection: both teams' `state.shape` dots in team colours, the momentum bar from `state.momentum` (grey with "No threat yet" when null), and three tiles: "PPDA ({home id})" and "PPDA ({away id})" over the last 10', plus "xG" as `home - away`.

  - Footer: "Every number here is computed by Python tools. The agents only explain them."
